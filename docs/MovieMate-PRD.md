## ۱. مسئله و چرایی

دو نفر (زوج/دوست) معمولاً ۱۵-۲۰ دقیقه وقت می‌گذارن تا تصمیم بگیرن چه فیلمی با هم ببینن — نه به‌خاطر کمبود گزینه، بلکه به‌خاطر نبود یک ابزار که سلیقه‌ی هر دو نفر رو همزمان در نظر بگیره. اپ‌های موجود (Letterboxd, IMDb) تک‌کاربره طراحی شدن؛ streaming appها فقط پیشنهاد فردی می‌دن.

**فرضیه اصلی**: اگر یک اپ بتونه تقاطع سلیقه‌ی دو نفر رو محاسبه کنه و تصمیم‌گیری رو به یک لحظه‌ی مشترک و کوتاه تبدیل کنه، مشکل "چی ببینیم؟" حل میشه و علاوه بر اون یک عادت روزانه‌ی مشترک ساخته میشه.

---

## ۲. کاربر هدف

- زوج یا دو دوست صمیمی که **از قبل همدیگر رو می‌شناسن** (نه matching با غریبه)
- هر دو گوشی اندروید دارن
- به‌طور منظم (حداقل هفته‌ای ۱-۲ بار) با هم فیلم می‌بینن یا می‌خوان این عادت رو بسازن
- زبان اپ: انگلیسی (کاربر انگلیسی‌زبان)

## ۳. هدف و معیار موفقیت (KPIs — ماه اول)

| معیار | هدف |
|---|---|
| Downloads | 100-500 |
| DAU | 50-100 |
| Day-1 Retention | >50% |
| Day-7 Retention | >40% (هدف بلندپروازانه‌تر با retention layer: 50%) |
| Day-3 Return Rate | >70% (با collaborative framing) |
| Crash Rate | <0.1% |
| زمان تولید recommendation | <500ms |
| API success rate | >99% |

> **نکته روش‌شناسی**: این اعداد فرضیات اولیه هستن، نه داده‌ی اندازه‌گیری‌شده. باید بعد از launch با داده‌ی واقعی validate بشن.

## ۴. مرز صریح Scope — نسخه ۱ (v1 / MVP)

### ✅ داخل Scope
- ثبت‌نام دو نفره با کد دعوت (invite code)
- Rating اولیه (~۱۰ فیلم) برای هر کاربر
- الگوریتم recommendation بر اساس تقاطع ژانر + امتیاز مشابه
- یک پیشنهاد روزانه (daily match) در ساعت مشخص، **یکی‌یکی نشون داده میشه** (نه چند گزینه هم‌زمان) **[UPDATE — بخش ۷.۱]**
- Watchlist مشترک با وضعیت‌های چندگانه **[UPDATE — بخش ۷.۴، جزئیات جدید]**
- علامت‌گذاری "دیده شد" — **دستی**، نه خودکار (بدون اتصال calendar/streaming) **[UPDATE]**
- Collaborative framing: "Tell partner" به‌جای فقط "Add to watchlist"
- **تعهد متقابل الزامی**: هر دو نفر باید تایید کنن قبل از رفتن به مرحله‌ی زمان‌بندی **[UPDATE — بخش ۷.۲]**
- Post-watch: رتینگ مشترک (Taste Dial) + واکنش کوتاه + پیشنهاد فیلم بعدی
- Notification پایه (partner activity, daily match, reminder مشترک)
- ۵ سناریوی edge case مستند‌شده (ALI-73): happy path, waiting for partner, incomplete preferences, no matches, error states

### ❌ خارج از Scope (v1)
- Matching با غریبه / کشف دوست جدید (Phase 2)
- بیش از ۲ نفر در یک پروفایل مشترک
- iOS (فقط Android در v1)
- ورود اجتماعی (Google/Apple Sign-In) — تصمیم باز، پیش‌فرض: فقط Email/Password در v1
- تماشای هم‌زمان داخل اپ (in-app sync watch / watch party)
- چت کامل بین دو کاربر (فقط quick reaction کوتاه، نه chat thread)
- زیرنویس یا لینک مستقیم به سرویس‌های streaming
- اتصال به تقویم یا سرویس‌های streaming برای تشخیص خودکار "دیده شد" — **تصمیم صریح تاییدشده** (نه فقط فرض) **[UPDATE]**
- پشتیبانی چندزبانه (فقط انگلیسی)
- ۳ پیشنهاد هم‌زمان برای انتخاب — **رد شده** به‌دلیل ریسک اختلاف بین دو نفر؛ فقط به‌عنوان fallback بعد از ۳ بار رد یک‌به‌یک ظاهر میشه **[UPDATE — بخش ۷.۱]**
- گیمیفیکیشن سنگین روی Watchlist (بج، امتیاز جمع‌شونده) — **تصمیم صریح رد شده**؛ تمرکز باید روی رابطه بمونه نه روی عدد **[UPDATE — بخش ۷.۴]**

## ۵. Non-Goals (عمداً نمی‌سازیم، حتی در آینده نزدیک)

- این اپ **جایگزین** Letterboxd/IMDb برای review‌نویسی حرفه‌ای نیست
- این اپ یک social network فیلم نیست (بدون فید عمومی، بدون follow کردن غریبه‌ها)
- بدون دیتای واقعی کاربر، هیچ ادعای دقت الگوریتمی خاصی نمی‌کنیم — این یک فرض قابل تست است، نه یک قطعیت اثبات‌شده

## ۶. User Journey اصلی — [UPDATE: ترتیب اصلاح‌شده]

> **تغییر مهم نسبت به v1**: ترتیب قبلی (Sign up → Invite → Rate) به دلیل یک اصل شناخته‌شده‌ی UX onboarding (نشون دادن ارزش قبل از خواستن تعهد) اصلاح شد.

```
سمت علی:
1. Welcome / Sign up
2. Rate ~10 films (تنها)
3. Invite partner (تولید کد، اشتراک‌گذاری)
4. [حالت انتظار — شریک هنوز نپیوسته/rate نکرده]

سمت سارا:
5. دریافت نوتیفیکیشن دعوت
6. Join با کد
7. Rate ~10 films (تنها)

مشترک:
8. Notification: "Today's match is ready" — فقط وقتی هر دو rate کرده باشن
9. صفحه‌ی Match — هر دو باید جدا "We're in" بزنن (تعهد متقابل، نه یک‌طرفه)
10. صفحه‌ی Reminder/زمان‌بندی — نوتیف به هر دو
11. [دستی: کاربر باید بزنه "We watched it"]
12. Taste Dial rating screen — هر دو امتیاز میدن
13. برگشت به Home — تیزر محوی از پیشنهاد فردا + دسترسی به Watchlist/Us
```

جزئیات کامل (۵ سناریو + edge caseها): ALI-73. جزئیات کامل happy path و پروتوتایپ: ALI-77.

## ۷. تصمیمات محصولی جدید (از جلسات طراحی بعد از v1)

### ۷.۱ — منطق پیشنهاد روزانه: یکی‌یکی، نه چندتایی

**تصمیم**: به‌جای نمایش ۳ پیشنهاد هم‌زمان (که در ابتدا بررسی شد)، اپ **یک پیشنهاد در لحظه** نشون میده.

```
پیشنهاد ۱ (بالاترین امتیاز) → اگه رد شد →
پیشنهاد ۲ → اگه رد شد →
پیشنهاد ۳ → اگه رد شد →
صفحه‌ی fallback: هر ۳ گزینه کنار هم (آخرین راه‌حل، نه پیشنهاد اول) — یا انتخاب یا صبر برای فردا
```

**چرا**: نمایش هم‌زمان چند گزینه ریسک اختلاف‌نظر بین دو نفر رو ایجاد می‌کنه — دقیقاً مشکلی که اپ قراره حلش کنه، نه بازتولیدش کنه.

### ۷.۲ — تعهد متقابل الزامی

روی صفحه‌ی match، **هر دو نفر** باید جدا دکمه‌ی "We're in" رو بزنن. مرحله‌ی بعدی (زمان‌بندی/reminder) فقط بعد از تایید هر دو باز میشه. این جلوی تصمیم‌گیری یک‌طرفه رو می‌گیره.

### ۷.۳ — رتینگ: Taste Dial به‌جای ۵ ستاره

**تصمیم**: سیستم رتینگ اصلی از ۵ ستاره‌ی گسسته به یک **اسلایدر پیوسته‌ی ۰ تا ۱۰۰** تغییر کرد.

- برچسب پویا: ۰-۲۰ «Not for us» / ۲۱-۵۰ «It was fine» / ۵۱-۷۵ «Really good» / ۷۶-۱۰۰ «Obsessed»
- امتیاز هر دو نفر روی یک نوار مشترک قابل مقایسه
- **اثر روی الگوریتم**: ورودی recommendation engine باید از عدد صحیح ۱-۵ به عدد پیوسته‌ی ۰-۱۰۰ تغییر کنه — این روی فرمول امتیازدهی در بخش الگوریتم (۹) اثر می‌ذاره و باید قبل از شروع dev backend نهایی بشه.
- Emoji quick-reaction به‌عنوان مکمل *اختیاری* نگه داشته شد، نه جایگزین رتینگ اصلی.

### ۷.۴ — ویژگی‌های Watchlist (تصمیم جدید، قبلاً در PRD نبود)

هدف Watchlist: نه یک لیست ساده، بلکه محیطی که **هر دو نفر** رو درگیر نگه داره.

**دسته‌بندی سه‌گانه‌ی وضعیت** (نه یک لیست تخت):
```
Ready to watch   → هر دو "We're in" زدن (بالای لیست)
Waiting on you   → یکی تایید کرده، منتظر تایید نفر دوم
Watched          → هر دو Taste Dial ثبت کردن
```

**ویژگی‌های مشخص**:
1. **نمایش کارهای انجام‌نشده به‌عنوان تسک** — هر آیتم که رتینگ یا تایید دیدن معلق داره، به‌وضوح به‌عنوان یک "کار باقی‌مانده" نشون داده میشه (نه فقط یک آیتم منفعل در لیست)
2. **نشونه‌ی "کی اضافه کرد"** — هر آیتم می‌گه توسط کدوم نفر یا از کدوم match اضافه شده (partner activity visibility)
3. **اکشن سریع درون‌لیستی** — اگه یک نفر آیتمی اضافه/تایید کرده، نفر دیگه می‌تونه مستقیم از داخل لیست بزنه "I'm in too" بدون رفتن به صفحه‌ی جدا
4. **ورود دستی با جست‌وجو** — کاربر می‌تونه فیلمی که خودش پیدا کرده (نه فقط پیشنهاد الگوریتم) با جست‌وجو در دیتابیس (TMDB) اضافه کنه
5. **مرتب‌سازی بر اساس رضایت مشترک** — برای فیلم‌های Watched، پیش‌فرض مرتب‌سازی بر اساس **بالاترین امتیاز مشترک هر دو نفر** (میانگین یا حداقل دو Taste Dial) در بالای لیست — نه فقط بر اساس تاریخ
6. **نمایش دو امتیاز کنار هم** — برای آیتم‌های Watched، دو نشانگر Taste Dial روی یک نوار مشترک (نه دو عدد جدا) — تقویت مفهوم سلیقه‌ی مشترک

**تصمیم رد‌شده**: گیمیفیکیشن سنگین (بج، شمارنده‌ی جمع‌شونده) روی خود Watchlist — چون تمرکز محصول باید روی رابطه بمونه، نه روی جمع‌آوری عدد. (هم‌سو با تصمیم قبلی در بخش retention — ALI-74)

### ۷.۵ — صفحه‌ی پایان چرخه‌ی روزانه (Home بعد از رتینگ)

به‌جای یک پیام خنثی "منتظر باش"، این صفحه دو ویژگی داره:
- **تیزر بصری محو**: یک کارت فیلم blur‌شده با آیکون قفل و متن "Tomorrow's pick — hidden" برای ایجاد کنجکاوی (نه فقط انتظار بی‌محتوا)
- **دسترسی کامل ناوبری** — این صفحه یک dead-end نیست؛ کاربر می‌تونه از همینجا بره Watchlist یا Us

## ۹. Data Model — خلاصه سطح بالا [UPDATE: تغییر نوع rating]

**Collections اصلی (Firestore)**:
- `users` — اطلاعات حساب فردی
- `pairs` (یا `profiles`) — پروفایل مشترک دو نفره، شامل invite code، وضعیت اتصال
- `ratings` — رتینگ هر کاربر روی هر فیلم (userId, filmId, **score: 0-100 [تغییر از integer 1-5]**, timestamp)
- `matches` — نتیجه‌ی محاسبه‌شده‌ی recommendation (pairId, filmId, score, reason, status: suggested/watched/dismissed, **commitStatus: {userA: bool, userB: bool} [جدید — برای تعهد متقابل]**)

> **[UPDATE] تعریف دقیق "Match" برای گزارش‌گیری و UI**: در هر گزارش یا آمار (مثلاً صفحه‌ی Us، بخش "Matches")، منظور از یک "Match" فقط فیلمی است که **هر دو کاربر مستقل commitStatus=true زده باشند** (هر دو "We're in" گفته‌اند) — نه صرفاً فیلمی که الگوریتم پیشنهاد داده. یک پیشنهاد که فقط یک نفر تایید کرده یا هیچ‌کدام تایید نکرده‌اند، در این شمارش لحاظ نمی‌شود. این تمایز مهم است چون تعداد پیشنهادهای الگوریتم به‌خودی‌خود معنادار نیست (فقط تعداد روزهای فعال اپ را نشان می‌دهد)، در حالی‌که تعداد تعهدهای متقابل واقعاً بازتاب رابطه است. UI باید این را با برچسبی مثل «Matches — both confirmed» یا توضیح کوتاه شفاف کند.
- `watchlist` — فیلم‌های اضافه‌شده با وضعیت (**pending/ready/watched — بازتعریف‌شده مطابق بخش ۷.۴**)، `addedBy` (کدوم کاربر اضافه کرده)
- `reactions` — واکنش کوتاه بعد از تماشا (اختیاری، مکمل Taste Dial)

**منبع محتوا/متادیتا — [UPDATE: تصمیم نهایی]**: TMDB API، به‌عنوان تنها منبع متادیتای فیلم (پوستر، خلاصه، ژانر، بازیگر، سال، امتیاز). این با معماری «فقط نمایش» اپ هم‌خونه — هیچ فایل ویدیو دانلود یا هاست نمی‌شه، هیچ اکشنی (پخش/دانلود) روی خود فیلم وجود نداره، فقط متادیتا نمایش داده می‌شه.

**جزئیات فنی TMDB که روی طراحی اثر دارن**:
- رایگان برای استفاده‌ی غیرتجاری با attribution؛ اگر اپ تجاری/درآمدزا بشه، لایسنس تجاری ۱۴۹ دلار/ماه (برای درآمد سالانه زیر ۱ میلیون دلار)
- Rate limit ~۴۰-۵۰ درخواست/ثانیه به‌ازای IP — برای مقیاس MVP کافیه
- **الزام Attribution**: باید لوگو/نام TMDB جایی در اپ (صفحه‌ی About) نمایش داده بشه
- بدون پوشش قوی برای «کجا استریم کن» — هم‌سو با تصمیم قبلی (بدون لینک مستقیم به streaming در scope)

**سوال باز قبلی — حالا جواب دارد**: آیا TMDB metadata در Firestore cache میشه؟ **بله، اما طبق Terms of Use رسمی TMDB حداکثر ۶ ماه** — این یک محدودیت قانونی است، نه یک تصمیم دلخواه؛ باید در طراحی cache invalidation (ALI-61/62) رعایت بشه.

## ۱۰. الزامات غیرعملکردی (Non-Functional Requirements)

| حوزه | الزام |
|---|---|
| Performance | تولید recommendation زیر ۵۰۰ms |
| Availability | API success rate بالای ۹۹٪ |
| Offline behavior | **[تعریف‌نشده — نیاز به تصمیم]**: آیا rating در حالت آفلاین queue میشه؟ |

| "Watched" detection | **صراحتاً دستی است** — بدون اتصال calendar/streaming در v1، این یک تصمیم تاییدشده است نه یک محدودیت موقت |

## ۱۱. Definition of Done — معیار آماده بودن v1

v1 وقتی "آماده" حساب میشه که همه‌ی موارد زیر برقرار باشن:

- [ ] هر ۵ سناریوی ALI-73 قابل تست و بدون crash
- [ ] happy path کامل (ALI-77) بدون گیر کردن قابل تکمیل توسط کاربر واقعی باشه

## ۱۳. ریسک‌ها

- **ریسک الگوریتمی**: اگر دو کاربر سلیقه‌ی کاملاً متفاوت داشته باشن (سناریو "No Matches" در ALI-73)، engagement ممکنه افت کنه. Mitigation فعلی: پیام تشویقی + نمایش سلیقه‌ی هر دو طرف، ولی این یک فرض تست‌نشده است.
- **ریسک retention**: تمام اعداد KPI (Day-7: 40-50%) فرضی هستن؛ بدون داده‌ی واقعی صنعت مشابه (dating apps دو نفره، couple apps) قابل benchmark نیستن به‌طور دقیق.
- **ریسک scope creep**: با ۱۸+ issue فعال با priority بالا، خطر واقعی اینه که M2 (retention) قبل از تکمیل M1 (core) شروع بشه. این ریسک هنوز باز است.
- **ریسک جدید — پیچیدگی تعهد متقابل**: نیاز به هم‌زمانی تایید دو کاربر (هر دو "We're in") پیچیدگی state management سمت backend رو بالا می‌بره؛ باید در طراحی schema (ALI-62) به‌دقت مدل‌سازی بشه.
